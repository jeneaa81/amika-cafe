# ADR-0002: Схема данных и политики безопасности Row Level Security (RLS) для предзаказов и карт лояльности

## Статус
Принято (Accepted)

## Контекст и проблематика
Приложение Amika Café работает в двух контурах:
1. **Гостевой контур (Telegram Mini App):** доступен любому пользователю Telegram с публичным `anon_key` Supabase.
2. **Служебный контур (Экран бариста и панель администратора):** доступен сотрудникам кофейни на планшете/ПК.

Без разграничения прав на уровне базы данных возникают критические уязвимости:
- Гость может просмотреть телефоны и имена других клиентов из таблицы `orders`.
- Гость может накрутить себе бесплатные чашки в `loyalty_cards`.
- Злоумышленник может массово создавать спам-заказы или менять их статусы.

### Факторы принятия решений (Decision Drivers):
1. **Защита персональных данных:** Номера телефонов и история заказов не должны быть публично доступны.
2. **Целостность программы лояльности:** Баланс чашек (0..6) гость может только просматривать. Править его может только администратор.
3. **Бесшовный UX без логина/пароля:** Клиенту не нужно вводить пароли или получать SMS-коды — идентификация происходит автоматически через `telegram_user_id` Telegram WebApp SDK.

## Рассмотренные варианты

### Вариант 1: Полностью открытый доступ (No RLS)
- **Плюсы:** Быстрый старт.
- **Минусы:** Нулевая безопасность. Любой человек через DevTools браузера может переписать баланс чашек или удалить чужие заказы.

### Вариант 2: Стандартная аутентификация Supabase Auth (Email / Телефон + SMS)
- **Плюсы:** Коробочная безопасность Supabase.
- **Минусы:** Огромное трение для гостя кофейни (вводить email или ждать SMS ради чашки кофе на бегу). Неприемлемо для формата Click & Collect.

### Вариант 3: Идентификация по Telegram WebApp ID + Строгие политики PostgreSQL RLS + PIN-сессия персонала
- **Плюсы:**
  - Нулевое трение для гостя: его ID автоматически предоставляется Telegram (`window.Telegram.WebApp.initDataUnsafe.user.id`).
  - Строгие RLS-политики на уровне PostgreSQL:
    - `orders`: гость может вставлять заказы со своим `telegram_user_id` и читать только свои заказы.
    - `orders`: обновлять статус (`status = 'ready' / 'completed'`) разрешено только бариста/админу (через защищенный service-токен или валидированную функцию с PIN-кодом).
    - `loyalty_cards`: гость может только читать свою карту (`SELECT`). Обновление баланса (`UPDATE`) разрешено только администратору.
- **Минусы:** Требуется создание RLS-правил и сервисной функции проверки PIN-кода администратора в базе.

## Решение
**Выбран Вариант 3 (Telegram Identity + PostgreSQL RLS + PIN-авторизация персонала).**

### Схема таблиц:

#### Таблица `public.orders`
- `id`: `text` (Primary Key, напр. `#102`)
- `telegram_user_id`: `int8` (ID гостя в Telegram)
- `customer_name`: `text`
- `customer_phone`: `text`
- `items`: `jsonb` (состав напитков, дозировка Solo/Doppio, молоко, сиропы)
- `total_amount`: `numeric(10,2)`
- `pickup_time`: `text` (напр. "Peste 5 min")
- `payment_method`: `text` (`'pickup'` / `'mia'`)
- `status`: `text` (Default `'new'`, переходы: `'preparing'`, `'ready'`, `'completed'`, `'cancelled'`)
- `created_at`: `timestamptz` (Default `now()`)

#### Таблица `public.loyalty_cards`
- `card_number`: `text` (Primary Key, напр. `AMIKA-8492`)
- `telegram_user_id`: `int8` (Unique, ID гостя)
- `current_stamps`: `int2` (0 to 6)
- `total_free_earned`: `int4` (Default 0)
- `updated_at`: `timestamptz`

## Последствия
- Полная конфиденциальность клиентских номеров телефонов.
- Невозможность накрутки подарочных напитков с клиентской стороны.
- Бариста и администратор работают через единый защищенный слой доступа.
